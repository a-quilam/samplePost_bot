# Poster — Telegram-бот конструктор постов

Однопользовательский бот: проходит все 9 полей поста, показывает превью,
помогает с правками — и по кнопке «Готово» присылает готовый пост в личный
чат. Черновики хранятся локально бессрочно и не теряются при выходе
из диалога. Управление идёт через один постоянный экран (Stage 11).

## Как это работает

```
Пользователь (личный чат)
  │  «✏️ Создать пост» или /create_post
  │  Шаг 1 из 9 — Заголовок … Шаг 9 из 9 — Изображение
  │  (любой шаг можно пропустить: кнопка «Пропустить» или слово)
  │  превью — только заполненные поля, русские названия
  │  [✏️ Редактировать] [📄 Сохранить в черновики] [✅ Готово — получить пост]
  └──► «Готово — получить пост» → пост уходит в личный чат тем же кодом, что и превью
```

* **Превью идентично готовому посту** — сводку собирают одни и те же
  функции (`build_post_summary`/`send_post`), тексты совпадают дословно
  (HTML-форматирование, типографика при вводе, разбивка длинных текстов
  и альбомы — общие).
* **Все 9 полей** проходятся последовательно, шаг и имя поля всегда
  видны («Шаг 3 из 9 — Время начала»); пропуск пишет пустое поле,
  незаполненные поля в сводке не показываются. Время принимается в
  любых равноправных формах — «21:30», «21.30», «21,30», «2130»,
  «пол двенадцатого» — и хранится нормализованным («23:30»); переход
  на следующий шаг после принятого ввода виден сразу. Дату можно
  ввести текстом или выбрать кнопочным календарём (Stage 17) — поле
  и правила хранения одинаковые.
* **Черновики**: сохранение вручную, а также при выходах — «📝 Черновики»,
  `/cancel`, `/start`, `/help`, `/drafts`, повторное «Создать пост»,
  открытие другого черновика (незавершённый пост не теряется, обновление
  идёт той же записью — без копий). Есть пагинация и удаление.
  Хранятся **бессрочно**: автоматической очистки по возрасту нет —
  удалить черновик может только пользователь, из списка, с подтверждением.
* **Фото и альбомы**: одно фото сразу к превью; альбом собирается до
  «✅ Фото готово». Несколько фото и альбомов **накапливаются** в один
  набор — второй альбом или отдельные снимки добавляются к первому,
  ничего не теряется из-за порядка отправки; показанное превью
  принимает новые фото (одиночка обновляет превью, новый альбом
  начинает сбор). Набор больше лимита Telegram (10 снимков в медиа-группе)
  отправляется группами. Фото вне шага изображения (в текстовых шагах)
  не теряется молча — бот подсказывает, где его добавить.
* **Ошибки не теряют данные**: сбой отправки или БД оставляет введённое
  в памяти и в снимке WIP; прерванная отправка длинного поста при
  повторе досылает только недостаающую часть — без дублей.

## Единый экран (Stage 11)

* Всё управление — в одном постоянном сообщении-экране: оно
  перерисовывается через `editMessageText`, а не плодит новые сообщения.
  Если экран удалён или недоступен для правки — создаётся новый, а
  ссылка на экран в `user_states` обновляется; «Message is not modified»
  (повторное нажатие) — штатная ситуация.
* Каждое нажатие inline-кнопки получает ответ (`answer_callback_query`);
  устаревшие кнопки завершённого диалога безопасно отклоняются.
* **Экран следует за вводом** (Stage 16): когда пользователь переходит
  сообщением (команда `/drafts`, `/start` или текст кнопки меню, набранный
  ниже по чату — как после сохранения черновика), старое сообщение-экран
  удаляется best-effort, ссылка на него очищается (снимок WIP сохраняется),
  и ответ создаётся новым сообщением рядом с вводом — пользователь видит
  результат. Навигация кнопками на самом экране, как и раньше, правит
  экран на месте — дублей не появляется.
* Состояние разделено: диалог (`ConversationHandler`), данные поста
  (`user_data` + JSON-снимок в `user_states`), отображение (экран),
  временные сообщения, готовые результаты.

### Восстановление незавершённого поста (WIP)

* После каждого принятого изменения данных снимок WIP пишется в таблицу
  `user_states` — и только после подтверждённого сохранения удаляются
  временные сообщения ввода («сначала сохранить, потом удалять»).
* После рестарта в главном меню появляется кнопка **«▶️ Продолжить пост»**:
  диалог возвращается на тот же шаг (или к превью), экран редактируется
  на месте. Пустой (незаполненный) WIP не сохраняется и не воскресает.

### Кнопочный календарь даты (Stage 17)

На шаге «Дата» — и при правке даты из превью — под полем ввода есть три
кнопки: **«На этой неделе»**, **«На следующей неделе»**, **«Другая»**.
Текстовый ввод даты работает без изменений: «17.11.2026», «1711»,
«17 ноября», «сегодня», «завтра»; кнопка и текст пишут **одно и то же
поле**, состояние данных и WIP одинаковые.

Навигация: **Дата → Категория → Диапазон → Неделя → День**; на каждом
уровне есть «◀️ Назад». Интерфейс остаётся единым экраном: уровни
перерисовывают его через `editMessageText`, новых сообщений и второго
сценария создания поста не появляется.

Пример для 22.10.2026 (четверг):

* «На этой неделе» → `22.10 (чт)`, `23.10 (пт)`, `24.10 (сб)`,
  `25.10 (вс)` — прошедшие дни недели скрыты;
* «На следующей неделе» → `26.10 (пн)` … `01.11 (вс)`;
* «Другая» → `02.11–15.11`, `16.11–29.11`, кнопка «Дальше»;
* «Дальше» → пары месяцев: `Ноябрь 2026` / `Декабрь 2026`, затем
  `Январь 2027` / `Февраль 2027` и так далее;
* выбор месяца → недели этого месяца (неполные недели обрезаются по
  месяцу и горизонту) → конкретные дни. После двух диапазонов **30.11
  остаётся доступным**: первая пара начинается с ноября, а не с декабря.

Формат кнопки дня — строго `дд.мм (дв)`, например `17.11 (вт)`;
дни недели — `пн`, `вт`, `ср`, `чт`, `пт`, `сб`, `вс`. Диапазоны —
`дд.мм–дд.мм`, при переходе через год годы добавляются
(`29.12.2026–11.01.2027`), одиночный день — `30.11`. Месяцы подписаны
по-русски с годом.

Горизонт — **12 календарных месяцев от сегодняшней даты включительно**
(календарное прибавление, а не фиксированные 365 дней): для 22.10.2026
последняя доступная дата — 22.10.2027, для 29.02.2028 — 28.02.2029.
«Сегодня» считается в зоне приложения (`Europe/Moscow`), общей
с текстовым парсером. Последняя пара месяцев может содержать один
месяц, если второй целиком за горизонтом — пустые месяцы не
показываются.

Безопасность и устойчивость:

* callback-данные содержат только индексы и ISO-даты, не пользовательский
  текст, и укладываются в лимит Telegram (64 байта);
* подделанный callback не может сохранить дату вне
  `[сегодня, сегодня + 12 календарных месяцев]`;
* если календарь открыт до полуночи, а кнопка нажата после — ставшая
  прошедшей дата не сохраняется: бот объясняет причину и перерисовывает
  актуальный корень календаря;
* повторное нажатие и устаревшие кнопки безопасны; если экран удалён
  или недоступен для правки, он создаётся заново, дальнейшая навигация
  идёт уже в новом экране, а при следующем сохранении WIP обновляется
  и ссылка в БД;
* выбор дня кнопкой сохраняется в то же поле, что и текст, после чего
  бот переходит к следующему шагу (при правке — возвращается к превью).

### Какие сообщения очищаются автоматически

* введённые пользователем текст/фото — после подтверждённого сохранения;
* **неудачные попытки ввода** (ошибка формата, «Некорректный формат») —
  после того как поле надёжно принято: их идентификаторы помнятся в
  состоянии сценария по полю и удаляются вместе с принятым вводом;
  при сбое базы ничего не удаляется преждевременно (Stage 16);
* исходники фото и альбома — после сохранения всех `file_id` (шаг
  «✅ Фото готово» или одиночное фото);
* старые версии превью — при следующем показе превью и при успешной
  отправке готового поста; при сбое превью остаётся в чате как опора;
* `/start` — его сообщение удаляется после обновления экрана.

**Никогда не удаляются**: готовые посты, черновики, экран управления.

## Стек

* Python 3.13+ (проверено на Python 3.14),
  [python-telegram-bot](https://python-telegram-bot.org) 21–22
  (асинхронный API, `ConversationHandler`; проверено на 22.8).
  `JobQueue` отключён явно (`job_queue(None)`): периодических задач нет,
  APScheduler не требуется (extra `[job-queue]` в зависимостях не ставится).
  Разовое предупреждение «No JobQueue set up» при старте — ожидаемое
  и безвредное.
* SQLAlchemy 2.0 (typed `Mapped[]`), SQLite (WAL, busy timeout),
* Развёртывание: локально или Docker (`Dockerfile`, `docker-compose.yml`),
* Качество: ruff, black, mypy, `unittest` (без внешних сервисов).

## Быстрый старт (локально)

```bash
cd Poster
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -r requirements-dev.txt   # для make check (опционально)

cp .env.example .env       # и заполнить TELEGRAM_BOT_TOKEN (секрет в git не попадает)

python bot.py              # или: make run PYTHON=.venv/bin/python
```

### Остановка

Ctrl+C в терминале — polling прерывается, все данные остаются в SQLite
(ничего не нужно «досохранять» вручную).

## Конфигурация (`.env`)

См. [.env.example](.env.example) — файл описывает каждую переменную.
Обязательна только `TELEGRAM_BOT_TOKEN` (от @BotFather); `DATABASE_URL`
и `LOG_LEVEL` опциональны. Бот работает в личном чате: никакие
ID чатов и списки администраторов не нужны.

* `.env` не коммитится и не публикуется; в git — только `.env.example`
  без значений;
* токен не пишется в логи: уровень httpx принудительно `WARNING`, а сам
  токен вычищается из сообщений и трассировок (`SecretScrubFilter`).

## База данных и резервные копии

* Рабочая база — **`Poster/post_bot.db`**, путь привязан к каталогу
  модуля, а НЕ к рабочей директории: запуск из `Poster/`, из корня
  репозитория, из IDE, из launchd/systemd использует один и тот же файл
  и не создаёт случайных баз в чужих каталогах.
* Путь можно переопределить переменной `DATABASE_URL`
  (в Docker: `sqlite:////app/data/post_bot.db` в `docker-compose.yml`).
* При подключении выставляются `journal_mode=WAL`, `synchronous=NORMAL`,
  `foreign_keys=ON` и busy timeout — обработчики работают параллельно,
  а внешние ключи проверяет сама SQLite.
* Схему меняют **нумерованные миграции** (`migrations.py`): журнал
  `schema_migrations`, контрольные суммы DDL, одна транзакция на запуск,
  защита от конкурентного старта. Повторный запуск ничего не применяет
  заново. Подробно — [docs/migrations.md](docs/migrations.md).
* Легаси-функция `_migrate()` осталась только для очень старых `drafts`
  (добавляет `photos`, `formats`, `updated_at`); новые изменения схемы идут
  только через `migrations.py`. В штатном `init_db()` миграции выполняются
  первыми, поэтому `create_all` создаёт только недостающие легаси-таблицы
  `drafts`/`user_states`; новые таблицы уже существуют.
* Stage 19A добавил инфраструктурные `users`, `places`, `place_names`;
  Telegram-интерфейса у них пока нет. Фотографии остаются вложениями
  анонса (`drafts.photos`), а не кирпичиками/полями шаблона.
* **Черновики хранятся бессрочно** (Stage 14): автоматической очистки
  по возрасту нет, фоновых задач у бота нет. Удаление — только вручную
  из списка черновиков, с подтверждением; черновики разных записей
  изолированы. Поле `updated_at` — informational, время последнего
  редактирования.
* База данных не хранится в git.

## Проверки и приёмка

```bash
pip install -r requirements-dev.txt
make check          # приёмка перед релизом: ruff + black + mypy + все тесты
```

`make check` (= `make accept`) — единый релизный прогон, выполняется
полностью локально, без живого Telegram, токена и пользовательской базы;
тот же прогон автоматически выполняется на GitHub Actions (см. раздел
«Автоматические проверки»):

* линтинг (ruff, black) и типизация (mypy);
* unit- и интеграционные тесты: настоящий `Application.process_update`
  поверх FakeBot (сеть недоступна) и временной SQLite;
* критические сценарии единого экрана (Stage 11, 24 сценария),
  сбои отправки и рестарты (Stage 12);
* smoke-запуск `bot.main()` из любого каталога с фиктивным токеном
  и заблокированной сетью (Stage 13);
* миграции на временных базах со схемами прошлых версий (Stage 13);
* Stage 19A: журнал миграций, откат сбойной миграции, конкурентный запуск,
  ограничения SQLite (UNIQUE/CHECK/FK), сохранность старых черновиков/WIP
  и неизменность настоящей `post_bot.db`.

Или по отдельности (из каталога `Poster`):

```bash
ruff check .
black --check .
mypy .
python -W ignore::DeprecationWarning -m unittest discover -s tests
make format        # автоформатирование (black + ruff --fix)
```

## Автоматические проверки (GitHub Actions)

Каждый push в `main` и каждый Pull Request в `main` автоматически
проверяются GitHub Actions (workflow [`.github/workflows/ci.yml`](../.github/workflows/ci.yml));
запуск вручную — через `workflow_dispatch` (кнопка «Run workflow»
на вкладке **Actions** репозитория).

* **Что выполняется**: на Ubuntu с Python 3.13 и 3.14 ставятся зависимости
  из `requirements.txt` + `requirements-dev.txt` и запускается
  `make check` — линтинг (ruff, black), типизация (mypy) и все тесты:
  интеграции поверх FakeBot, миграции на временных SQLite, smoke-запуск
  `bot.main()` с фиктивным токеном и заблокированной сетью.
  (`make accept` — алиас `make check`, поэтому в CI прогоняется один раз.)
* **Где смотреть результат**: вкладка **Actions** репозитория → запуск
  **CI** → нужный прогон по версии Python; логи пошаговые, статус —
  зелёная галочка у коммита.
* **Локально те же проверки**: `make check PYTHON=.venv/bin/python`
  из каталога `Poster`.
* **Без секретов и без Telegram**: `.env` в CI не нужен — тесты сами
  подставляют фиктивный токен (`tests/__init__.py`), Telegram Bot
  подменяется FakeBot, базы — временные SQLite, сеть заблокирована.
  Реальный бот в CI не запускается, действующая `post_bot.db`
  не затрагивается.

## Команды бота

| Команда / кнопка | Назначение |
|---------|-----------|
| `/start` | главное меню (существующий экран обновляется) |
| «✏️ Создать пост», `/create_post` | диалог создания поста (9 шагов → превью) |
| «▶️ Продолжить пост» | восстановление незавершённого поста после рестарта |
| «📝 Черновики», `/drafts` | список черновиков (постранично) |
| `/cancel` | отменить текущий диалог (пост сохраняется) |
| `/help` | справка |

Команды `/start`, `/help`, `/drafts`, `/cancel`, отправленные во время
создания или редактирования поста, сохраняют незавершённый пост и завершают
диалог: ответ бота всегда означает, что из создания вышли.

### Длина ввода

* **Искусственных лимитов длины полей нет** — заголовок, описание, место,
  контакт и ссылка вводятся целиком, текст не обрезается молча
  (ограничений вроде 100/200/500 символов в валидаторах нет).
* Реальные ограничения — платформенные: одно входящее сообщение Telegram
  не длиннее **4096 символов**, поэтому поле не может быть длиннее одного
  сообщения (это лимит API, а не наше правило).
* Длинный итоговый пост разбивается на несколько сообщений по **4000
  символов** (`split_long_text`): разбивка не режет Unicode-символы и
  HTML-теги, части отправляются по порядку (проверено Stage 10).
* Пост с фото уходит подписью к фото; лимит подписи Telegram — **1024
  символа** (у нас `CAPTION_TEXT_LIMIT` = 1000 с запасом). Если текст
  длиннее — фото отправляется без подписи, а полный текст идёт
  отдельными сообщениями по 4000 символов: текст не обрезается.
* Дата, время и ссылка проверяются на **корректность формата**, но не
  на длину.

## Логи

* Все логи — в **`Poster/logs/bot.log`**, путь привязан к каталогу проекта
  (как SQLite): запуск из любого каталога пишет в один и тот же файл,
  случайные `logs/` не создаются.
* Ротация: активный файл до **5 МБ**, хранится до **5 архивов**
  (`bot.log.1` … `bot.log.5`), старые удаляются автоматически; Unicode
  переживает границу ротации (записи не режутся посередине).
* Уровень — через `LOG_LEVEL` (по умолчанию `INFO`); логи идут и в консоль.
* Безопасность: токен бота вычищается из сообщений и трассировок
  (`SecretScrubFilter`) даже при `LOG_LEVEL=DEBUG`; полный текст
  пользовательского ввода в логи не пишется — только событие, поле
  и длина (см. `log_config.py`).

## Структура кода

```
bot.py                  сборка приложения и обработчиков, запуск
config.py               чтение .env (валидация при импорте)
database.py             engine, PRAGMA, путь к SQLite, вызов миграций
migrations.py           нумерованные миграции, журнал schema_migrations
models.py               SQLAlchemy-модели Draft, UserState, User, Place, PlaceName
user_store.py           UPSERT пользователя по Telegram user ID
place_store.py          нормализация названия, создание места + канонического имени
errors.py               глобальный обработчик ошибок (лог + ответ пользователю)
handlers/
  post_creation.py      диалог создания/редактирования поста (ConversationHandler),
                        единый экран, превью, отправка готового поста, WIP
  drafts.py             список черновиков (пагинация), удаление, листание
  main_menu.py          /start, /help, /drafts, клавиатура главного меню
  callbacks.py          возврат в главное меню из inline-кнопок
utils/
  screen.py             единый экран, временные сообщения, снимок WIP в БД
  tg_html/форматтеры    HTML-форматирование, типографика, валидаторы, typed-хелперы PTB
tests/                  unit- и интеграционные тесты: FakeBot, временные
                        SQLite, 24 сценария экрана, smoke-запуск, миграции
```
