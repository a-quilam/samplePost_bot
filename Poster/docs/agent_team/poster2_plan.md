# Poster 2.0 — план реализации

**Статус:** `approved` — утверждён владельцем 2026-10-27; этапы S1–S5
выполняются последовательно.
**Этап:** P0 завершён. Ни один этап S1–S5 не начат на момент этой редакции.
**Дата:** исходный план 2026-10-26; корректировка и утверждение 2026-10-27.

План опирается на `poster2_spec.md`. Нумерация §N в критериях ниже
ссылается на разделы спецификации.

---

## 0. Общие правила для всех этапов

1. Один этап — один `poster-developer` в общей рабочей директории.
   Второй параллельный подагент (`poster-reviewer`/`poster-tester`) —
   только на чтение.
2. Целевые тесты — после каждого связанного изменения. Полный
   `make check PYTHON=.venv/bin/python` — минимум в конце **каждого** этапа
   и ещё раз после интеграции S5; ошибки нельзя «закрывать» отключением теста.
3. Запрещено: `make run`, `python bot.py`, `botctl.sh start|stop|restart`,
   изменение реальной `Poster/post_bot.db`, `.env`, `backups/`, force push.
4. Миграции 1–14 не менять. Миграции 15 (`bricks.description`, `[адрес]`) и
   16 (`announcement_drafts` без обязательного `place_id`, `origin`,
   множество live ID) **утверждены владельцем 2026-10-27**; фактические
   номера сверены с журналом (`LATEST_VERSION = 14`). Каждый DDL сначала
   тестируется на временной копии с FK, триггерами, данными; обязательны
   автоматические проверки целостности, rollback и резервное копирование.
   На реальной базе во время разработки миграции **не** исполняются.
5. Не «подгонять» тесты под ошибочное поведение. При удалении легаси
   заменять его тесты функциональными e2e для единого конструктора;
   документировать удалённое покрытие и не удалять тест общей подсистемы
   только потому, что он лежит в файле со старым названием.
6. Каждый этап заканчивается отчётом по шаблону
   (`Статус / Изменено / Проверки / Риски / Дальше`).
7. Независимая проверка: на **каждом** этапе S1–S5 обязателен прогон
   `poster-tester` (FakeBot + временный SQLite) и ревизия `poster-reviewer`.

### Блокирующие зависимости

```
Утверждение владельца получено 2026-10-27
                    │
                    ▼
S1 (домен) ──► S2 (меню и входы) ──► S3 (живой анонс)
                    │                        │
                    └──────────┬─────────────┘
                               ▼
                        S4 (фото и лимиты) ──► S5 (удаление легаси)
```

S1 больше не заблокирован: архитектура утверждена. Миграции 15/16
исполняются первыми в S1 на временных SQLite с проверками целостности и
rollback. Таблицы `drafts`/`user_states` не удаляются, пока не доказан
полный переход на новый конструктор и отсутствие зависимостей; DROP
возможен только отдельной документированной операцией с бэкапом.
S2 и S3 можно вести параллельно только при условии, что S3 не трогает
`main_menu.py`/`bot.py` (границы разведены ниже). S5 — строго после S2–S4.

**Зависимости:** утверждённые `poster2_spec.md` и `poster2_plan.md`.

- `Poster/announcement_wizard.py`

  не ломать другие сущности)

- `Poster/docs/migrations.md` (описание миграций)

менять `places`, `place_names`, `users`, `place_admins`, редактировать

**Работы:**

   пользовательский код `[адрес]` (не подменять на `[адрес_места]`);

## S3. Один экран конструктора: живой анонс, календарь, время

**Цель:** с первого вопроса верхний блок выглядит как **настоящий
анонс**, нижний — единственный служебный экран; после каждого значения
пост меняется; календарь сразу, время — быстрые кнопки. Декомпозиция
большого обработчика без ненужного нового конструктора.

**Ответственный:** `poster-developer`. Приёмка — `poster-reviewer`.

**Зависимости:** S1 (данные), S2 (точки входа). С S4 пересекается только
`template_compiler.py` (S3 добавляет `render_announcement`, S4 —
`measure_bricks`) и `delivery.py` (создаётся в S4); этапы идут
последовательно, поэтому конфликта нет.

**Границы:**
- Новые модули: `Poster/handlers/wizard_live.py` (живой анонс),
  `Poster/handlers/wizard_questions.py` (вопросы/календарь/время)
- `Poster/handlers/announcement_wizard.py` — вынос вопросов/рендера,
  регистрация единственного ConversationHandler остаётся
- `Poster/utils/calendar_view.py` (если нужна компактная сетка)
- `Poster/template_compiler.py` — единый рендер для live/final, строго
  буквальная статика; техническая `.` применяется **перед отправкой**, а
  не внутри компилятора значений кирпичиков
- `Poster/announcement_wizard.py` (только `evaluate_announcement_readiness`)
- `Poster/tests/test_poster2_live.py` (новый)

**Запрещено:** менять доставку и лимиты (это S4), менять
`send_rendered_post`, менять `main_menu.py`.

**Работы:**
1. Разбиение `handlers/announcement_wizard.py` (5514 стр.): вынести
   вопросы/календарь и живой экран; поведение не меняется на этом шаге
   (рефакторинг под зелёными тестами).
2. От первого вопроса: **сначала** настоящий отформатированный верхний
   анонс, **затем** нижний рабочий экран; при пустом live-тексте только
   техническая `.`. После каждого ответа обновлять верх через Telegram API
   и служебный экран; сохранить данные и подтверждённые ID. Обеспечить
   правильный порядок сообщений даже после полной пересборки медиа (§4).
3. Удаление ответов пользователя после подтверждённого сохранения
   (`drop_user_input`), кроме проблемного сценария S4.
4. Календарь — сразу экран вопроса даты (без кнопки «📅 Календарь»),
   компактная сетка, навигация по месяцам.
5. Время — кнопки 18:00 / 18:30 / 19:00 + ввод сообщением.
6. **Последний кирпичик → всегда шаг фотографий**, а не готовый пост;
   именно фото/«Без фотографий» завершает автоматически, без «Готово»,
   «Сформировать» или повторной отправки уже показанного верхнего блока.
   После завершения нижний экран предлагает правку данных, фотографий,
   extras, альтернативного имени площадки и переход в главное меню.
7. Переход в меню: анонс остаётся в истории, меню — новым сообщением.
8. Готовность: снять блокировку для анонса, где пропущены **все** кирпичики
   (решение владельца п.1, §5.6).
9. Рендер: статический текст шаблона сохраняется буквально — никакой
   постобработки/«чистки сирот» (решение владельца п.2, §6.1 п.3).
   Отдельный тест: шаблон с `//` и пропущенными `[дата]`/`[время]`
   даёт `//` в результате.
10. Пустой результат: Telegram-плейсхолдер `.` при отсутствии и текста,
     и фото, в том числе для live-верхнего блока; значения кирпичиков не
     меняются. В готовой доставке `publication_text` содержит то, что
     реально отправлено (§5.6).
11. Нижний служебный экран готового пустого анонса показывает короткую
    шутку из фиксированного набора при включённом юморе. В S3 обеспечить
    рендер текста и подготовить хук; фактический финальный сценарий и
    вероятностный модуль проверяются соответственно в S4 и S5.

**Критерии приёмки:**
- [ ] С **самого начала** верхний блок содержит фактический макет
      анонса, а не сводку; после каждого ответа/пропуска он обновляется,
      сохраняя форматирование и ссылки.
- [ ] Нижний экран — одно сообщение, без цепочки «шаг 1/2/3».
- [ ] Ответы пользователя удаляются, кроме случая превышения лимита.
- [ ] Календарь появляется сразу на вопросе даты.
- [ ] Кнопки времени 18:00/18:30/19:00 работают, ручной ввод тоже.
- [ ] Нет кнопки «Готово, получить пост» ни на одном экране.
- [ ] Новый анонс не меняет и не удаляет предыдущий; верхний блок

## S4. Фото, ограничения и финализация уже живого анонса

**Цель:** пользователь после всех кирпичиков присылает одно фото,
Telegram-альбом или нажимает «Без фотографий», после чего анонс **готов
автоматически**. Верх может быть медиаблоком из нескольких сообщений,
фото видны над текстом. Нельзя выдать повторную копию того же поста;
при превышении длины сохраняются исходные данные и входное сообщение.

**Ответственный:** `poster-developer`; независимая приёмка `poster-tester` и
`poster-reviewer` (FakeBot + крайние случаи + рестарт).

**Зависимости:** S3 (общий live presenter), S1 (ID верхнего блока,
доменный прогресс).

**Границы:** `Poster/handlers/wizard_photos.py` (новый),
`Poster/handlers/wizard_live.py`, `Poster/delivery.py` (вынос общего
доставщика), `Poster/template_compiler.py` (измерение видимого вклада),
`Poster/announcement_store.py` (live/final linkage),
`Poster/handlers/announcement_wizard.py` (подключение),
`Poster/tests/test_poster2_limits.py` и `test_poster2_delivery.py` (новые).

**Запрещено:** автосокращение, разрезание длинного поста на текстовые
сообщения, превышение **10 фото на весь анонс**, новый конструктор,
дублирующая отправка при финализации, удаление пользовательского текста в
проблемном сценарии. Не переносить `split_long_text` как обязательную часть
доставки.

**Работы:**

1. Перенести реально общие функции Telegram-доставки из легаси в
   `delivery.py`, убрать циклический импорт. Один сборщик payload для
   живого и готового поста; один алгоритм fingerprint и записи успешных ID.
2. Отдельный последний шаг фото с кнопкой «Без фотографий». Фото и альбом
   завершают автоматически после получения **всей** Telegram-партии; в
   дальнейшем добавление новых групп — через «Фотографии» готового поста.
3. Поддержать **окончательный максимум 10 фото на анонс** (решение
   владельца 2026-10-27), группируя по **2–10** на вызов `sendMediaGroup`
   (остаток из одного фото — отдельный `sendPhoto`). Показать все фото
   **сверху**, а текст ровно один раз — подписью **последнего** фотосегмента;
   Telegram-клиенты проверить на фактический порядок отображения. Попытка
   добавить 11-ю фотографию отклоняется с понятным объяснением, уже
   принятые фотографии сохраняются. Покрыть ограничение автотестами.
4. При смене состава блока сначала создать новую валидную группу/группы,
   сохранить ID **каждого** отправленного сообщения, поставить служебный
   экран ниже, потом очистить заменённые собственные сообщения. При 48-часовом
   ограничении честно сообщить, что старая копия могла сохраниться.
5. Разделить временные `live_message_ids` и frozen `publication_progress`;
   при финале, если верхняя версия уже точно доставлена и совпадает по
   payload/fingerprint, **признать существующие ID готовым постом, не
   посылать новый**. После рестарта не создавать двойной анонс и не удалять
   прошлую версию до успешной новой. При необходимости нового перехода
   состояния добавить отдельную миграцию после тестов триггеров: `sent`
   допустим только с `published_at`, frozen payload и подтверждёнными
   текущими `ids`; `previous_ids` относятся только к заменяемой версии.
6. Текст без фото — до 4096, с фото — до 1024 **после разбора entities**;
   Unicode/эмодзи/HTML и границы 1024/1025/4096/4097 проверять явно.
7. Проблемный экран: исходный текст и фото сохранить, вызвавшее превышение
   сообщение не удалять. Показать текущую длину и лимит, топ длинных
   кирпичиков, **«Изменить другой кирпичик»** и **«Без фотографий»**.
   После сокращения применить ожидавшую фотографию, не прося прислать её
   снова; при отказе от фото лимит вновь 4096.
8. Обработать Telegram `not modified`, `not found`, `RetryAfter`,
   `Forbidden`, частичную медиадоставку, падение между подтверждением API и
   записью в БД и неудачное удаление. Падение нельзя считать успехом.

**Приёмка:**

- [ ] 0 фото — текст до 4096, 1..10 фото — единый логический пост
      с текстом до 1024; 2–10 фото в одной группе, хвост из одного фото —
      отдельный `sendPhoto` (нельзя `sendMediaGroup` из 1 элемента).
- [ ] Попытка добавить 11-е фото отклоняется с объяснением; ранее принятые
      10 фото сохранены и не перезаписаны.
- [ ] Фото идут до текста, верх до нижнего экрана; после пересборки и
      рестарта порядок остаётся понятным; нет второго «готового» поста.
- [ ] Альбом обрабатывается целиком, до окончания партии готовность не
      наступает; «Без фотографий» сразу завершает без запроса «Готово».
- [ ] Текст в 4096/1024 на границе проходит; на 4097/1025 — проблемный
      экран. Сырые HTML-теги не считаются видимыми символами.
- [ ] Значения и фотографии в БД сохранились, вызвавшее ошибку сообщение
      осталось в чате; можно выбрать любой кирпичик для исправления.
- [ ] При превышении после фото доступны «Без фотографий», сокращение
      кирпичика и последующее автоматическое появление ранее принятого фото.
- [ ] Fingerprint, idempotency, dedup повторных callbacks/restarts;
      частичная доставка досылает только недостающее, старые сообщения
      удаляются **только** после успеха новой версии.
- [ ] Пустой итог без фото отправляется как `.`, с фото без подписи-точки;
      `publication_text` эквивалентен реально доставленному тексту.
- [ ] Не осталось разбиения длинного готового анонса на отдельные тексты.
