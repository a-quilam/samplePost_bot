### 1.3. Шаблоны и кирпичики — уже как данные (переиспользуем)

- Создаётся автоматически **только для места**: `place_store.create_place` →
  `create_standard_template_for_place` (`template_store.py:627`),
  бэкфилл — миграция 8 (`template_store.py:727`).
- Автосоздания **личного** шаблона новому пользователю нет.
- Встроенный текст (`template_types.py:47-56`):
  шапка `[название]`; тело `🗓 [дата] / 🕒 [время_начала] – [время_окончания] /
  📍 [место] / [адрес_места] / <пусто> / [описание]`;
  подвал `🔗 [ссылка_места]` + `📞 [контакт]`.
- **Расхождение с требованием 4:** ссылка площадки выводится отдельной
  строкой `🔗 [ссылка_места]`, а не как гиперссылка в названии места.
  Форма `[место]([ссылка_места])` грамматикой поддерживается, но в BUILTIN
  не используется.

### 1.5. Автоподстановка и вопросы

`build_questions` (`announcement_wizard.py:364-457`) идёт по снимку
шапка→тело→подвал, повтор кирпичика спрашивается один раз, известные
значения места (`place_context_values:242-259`, id 5/6/7) не спрашиваются,
все вопросы `required=False, allow_empty=True`. Это ровно требование 3,
кроме одного: id 5/6/7 **захардкожены** (`announcement_wizard.py:60-62`)
вместо поиска по коду.

### 1.6. Готовность и «пустой» анонс

`evaluate_announcement_readiness` (`announcement_wizard.py:199-238`) требует
непустой видимый текст и хотя бы одно заполненное значение, если в снимке
есть кирпичики. Значит анонс, где пропущено всё, готовым не считается.

**Решено владельцем (2026-10-27, дополнение п.1):** завершать анонс можно,
даже если пропущены **все** кирпичики. Проверка готовности больше не
блокирует переход. Обработка полностью пустого результата — §5.6.

### 1.7. Живой анонс

«Живого» анонса во время заполнения нет: превью обрезается до
`PREVIEW_VISIBLE_LIMIT = 1800` (`handlers/announcement_wizard.py:136,2958-2990`)
и живёт в служебном экране. Два сообщения используются только **после**
доставки: готовый анонс без клавиатуры + служебный экран действий
(`_render_delivered`, `handlers/announcement_wizard.py:3743-3805`).
Экран — один и тот же `utils/screen.py:render_screen` (editMessageText
с fallback на send), т.е. дисциплина «одно сообщение-экран» уже соблюдена.

### 1.8. Фотографии и лимиты

- Коллекция `announcement_drafts.photos` (JSON `file_id`), лимит
  `MAX_ANNOUNCEMENT_PHOTOS = 10` (`announcement_store.py:99`).
- Приём — только на `stage=preview/completed`; из альбома берётся
  `message.photo[-1]` (`handlers/announcement_wizard.py:4195`).
- Отправка `send_rendered_post` (`handlers/post_creation.py:1805-2040`):
  `MESSAGE_TEXT_LIMIT = 4000`, `CAPTION_TEXT_LIMIT = 1000`,
  `MEDIA_GROUP_LIMIT = 10` (`:1768-1773`).
- При превышении лимита текст **разбивается на несколько сообщений**
  (`:1935,1959-1995`). Требование 8 требует обратного: не резать, а
  остановить с объяснением и дать выбор.
- Лимиты занижены относительно Bot API (официально 4096 и 1024) — запас
  в 96 символов; в новой модели считаем по официальным значениям (§5.1).

Проверено по Bot API (core.telegram.org, 2026-10-26):
`sendMediaGroup` — 2–10 элементов; `editMessageMedia` — элемент альбома
редактируется только в рамках своего типа, состав альбома менять нельзя;
`editMessageCaption` — 0–1024 символа после разбора entities;
`deleteMessage` — только сообщения младше 48 часов.

### 1.9. Доступ к админке

`is_superadmin` (`permissions.py:23-31`) сравнивает **числовой**
`telegram_user_id` со списком `config.SUPERADMIN_USER_IDS`
(`config.py:22-57,83`), username не участвует. Видимость кнопки —
`_show_admin_button` (`handlers/main_menu.py:69-80`): любое исключение
глушится и кнопка молча исчезает. Вход `/admin` перепроверяет права
(`handlers/admin.py:2182-2204`). Причина «не вижу админку» поэтому имеет
как минимум пять разных объяснений (§7.5) — менять права наугад нельзя.

## 2. Схема компонентов единого конструктора

Один движок и один редактор, два равноправных входа. Отличается источник
снимка шаблона и стартовый контекст площадки; сам конструктор, валидаторы,
живой рендер, фото, редактирование и доставка **общие**. Вход с площадки
никогда не предлагает выбор шаблона: он привязан к площадке.

```

                                   │
        ┌──────────────────────────┴──────────────────────────┐
        │                                                     │
«📍 Создать для площадки»                        «📝 Создать по личному шаблону»
        │                                                     │
  places_picker (список+поиск+добавить)                personal_templates_picker
        │  тап по названию → сразу старт                      │  тап по названию → сразу старт
        │  (шаблон = стандартный шаблон площадки)      (CRUD шаблонов в том же разделе)
```

### 2.2. Правила слоёв (обязательны для всех этапов)

1. Telegram-слой не ищет кирпичики по текстовому коду — только по `brick_id`
   (уже соблюдается, `announcement_store.build_announcement_fields`).
2. Доменное состояние — только в `announcement_*`. `user_data` — только
   навигация (`screen` ref, страница, активный `brick_id`).
3. Все мутации — через CAS `_cas_update_draft` + `expected_revision`.
4. Рендер текста — только `template_compiler`; preview и доставка считаются
   **одной** функцией (сейчас расходятся: `_preview_summary_lines` против

5. Никаких `import` обработчик↔обработчик внутри функции: циклическая
   зависимость уже обходится так в `handlers/announcement_wizard.py:3950`.
   Вынос `send_rendered_post` в `delivery.py` её устраняет.

## 3. Состояния и переходы единого конструктора

Создание начинается **до** создания черновика: меню и справочники — это навигация,
а не фиктивные записи в `announcement_drafts`. После выбора зарегистрированной
площадки либо личного шаблона создаются черновик и неизменяемый снимок
шаблона. В режиме площадки выбирается **только** площадка, её шаблон уже
определён. При создании новой площадки она получает стандартный шаблон и
начинается тот же конструктор.

| Состояние | Нижний служебный экран | Верхний анонс | Переход |
|---|---|---|---|
| Навигация (ещё без черновика) | список площадок (сначала все, далее поиск и добавление) **или** список личных шаблонов с CRUD | отсутствует | выбор названия без подтверждения → создание снимка → вопросы |
| `questions` | вопрос очередного кирпичика, понятное описание, «Пропустить»; дата сразу календарём, время — 18:00 / 18:30 / 19:00 и ручной ввод | от первого момента **реальный рендер шаблона**, обновляется с ответами | ответ/пропуск → следующий кирпичик; после последнего → `photos` |
| `photos` (технически может использовать существующий `preview` с подэтапом) | «Пришлите фото/альбом или нажмите „Без фотографий“» | рендер без фото, при поступлении фото — медиаблок с текстом под фото | «Без фотографий» либо завершённая партия фото → автоматическая готовность |
| `length_problem` (подэтап) | причина и размер превышения, самые длинные кирпичики, «Изменить другой кирпичик», «Без фотографий» | последняя **валидная** версия видна; полученные текст/фото сохранены | сокращение/отказ от фото → повторная проверка → возврат в `photos` или готово |
| `completed` | отдельный экран управления готовым анонсом: править данные, фото, extras, альтернативное название площадки, перейти в меню | уже готовый пост без клавиатуры | правки копятся; «Применить изменения» выполняет замену версии; переход в меню оставляет результат |

Никакой кнопки «Готово, получить пост», «Сформировать» или подтверждения
финальной доставки нет. **Последний кирпичик ещё не завершает весь процесс:**
после него обязательно спрашиваются фотографии. Нажатие «Без фотографий»
либо завершение приёма одного фото/альбома сразу завершает анонс. Для фото
из нескольких отдельных отправок действует тот же редактор: следующая партия
может быть добавлена через раздел «Фотографии» готового анонса без повторного
прохода по кирпичикам; незаявленная кнопка подтверждения не вводится.

Все кирпичики, встречающиеся в снимке шаблона, предлагаются по порядку
шапка → тело → подвал с дедупликацией; **все можно пропустить**. Для
личного шаблона порядок строго сверху вниз по тексту шаблона, и кирпичик
«Место» может отсутствовать полностью. Автоподставленные значения
зарегистрированной площадки не переспрашиваются, но правятся позднее.

Устаревший callback/revision отклоняется без изменения данных. Вход в другое
меню не удаляет черновик. После перезапуска состояние восстанавливается из
БД, не через повторное создание снимка. Обработка только в личном чате
автора; группам/каналам данные не отправляются.

### 3.1. Телеграм-состояния

У единого ConversationHandler одна точка продолжения, независимо от источника
шаблона. Названия `AW_QUESTIONS`, `AW_PHOTOS`, `AW_READY`, `AW_EDIT` —
предлагаемые внутренние, но не обязательные. Старый `POST_CREATION` удаляется.
Снимки/значения хранятся доменным слоем; `user_data` — только навигация.

## 4. «Чат как приложение»: живой пост сверху, рабочий экран снизу

**Постоянный вид при создании:** логический верхний блок — настоящий анонс
с буквальным шаблоном, Telegram-разметкой, работающими ссылками и видимыми
фото по мере добавления; нижний блок — одно управляемое сообщение с вопросом,
пояснением и кнопками. «Верхний блок» может состоять из **нескольких**
сообщений Telegram при наличии альбомов. Он не содержит клавиатуры.

Порядок в истории чата принципиален: **медиа/пост сверху → служебный экран
ниже**. Telegram сохраняет хронологический порядок сообщений: редактирование
старого верхнего сообщения не сдвигает его, а отправка нового сдвигает.
Поэтому простого `live_message_id` недостаточно: нужен упорядоченный набор
`live_message_ids`, а при полной пересборке блока требуется переотправить
или восстановить нижний экран ниже новой версии, затем убрать устаревшие
служебные/предпросмотровые сообщения, где это возможно. Все подтверждённые
ID сохраняются; удаление **не** выполняется до успешного создания замены.

### 4.1. Жизненный цикл

| Событие | Требуемое поведение |
|---|---|
| выбор площадки/личного шаблона | создать снимок; отправить верхний рендер **до** нижнего вопроса; даже если содержимое пока пусто, применить технический placeholder `.`, не менять значения кирпичиков |
| ответ/пропуск | записать значение с CAS; при допустимой длине отредактировать верхний блок (если это возможно) и перерисовать нижний вопрос, не создавать лишних сообщений |
| приём фото/альбома | сохранить каждый `file_id`; показать фото **сверху**, текст подписи под ними; медиагруппы строятся партиями по 2–10 (хвост из 1 фото — `sendPhoto`), подпись только у последнего сегмента; обновить набор ID и обеспечить служебный экран ниже блока |
| превышение лимита | значения и фото сохранить, входное сообщение **не удалять**; оставить последнюю корректную живую версию и показать нижний проблемный экран |
| завершение без изменения содержимого | **не отправлять второй такой же анонс**: признать подтверждённый верхний блок готовой доставленной версией, зафиксировать его ID, текст, фото и fingerprint; убрать только временный интерфейсный мусор |
| завершение с несовпадающей/недоставленной версией | собрать новую версию, подтвердить доставку и лишь затем удалять устаревшую; повтор после сбоя досылает только недостающее, не удваивает подтверждённые сообщения |
| правка готового | открыть **новый служебный экран** управления; накопить изменения, отправить новую версию по «Применить изменения», только затем убрать прошлую копию; уже завершённые другие анонсы не трогать |
| переход в меню | оставить готовые анонсы в истории без клавиатур; показать меню **новым** служебным сообщением, предыдущий служебный экран убрать по возможности |
| перезапуск | восстановить из БД `draft_id`, упорядоченные верхние ID, состояние рабочего экрана и успешность операций; никакого повторного снимка или безусловной отправки дубликата |

### 4.2. Ограничения удаления и чистоты

- Удалять пользовательские ответы **только после подтверждения** сохранения
  и успешного отображения; в сценарии превышения лимита сохранять исходное
  сообщение, чтобы пользователь мог скопировать/исправить введённое.
- Завершённые результаты разных анонсов **никогда** не удаляются при создании
  следующего; старые версии **одного** редактируемого анонса можно заменить,
  если это технически разрешено Telegram (обычно ограничение удаления 48 ч).
- Если Telegram не разрешает убрать сообщение, считать это известным
  ограничением и кратко объяснить в нижнем экране; не скрывать оставшийся
  дубль под словом «заменён».
- Избегать повторной отправки на техническом рендере, двойном callback и
  рестарте. Предварительная фиксация намерения и подтверждённых операций
  должна отделять «живой предпросмотр» от `publication_progress` завершённой
  доставки; переход к `sent` не должен сам инициировать копию уже стоящего
  в чате поста.
- Для текста/медиа использовать один общий сборщик и сравнение с фактически
  отображённой версией. Удалять только собственные служебные сообщения
  и заменяемую версию **того же** анонса, никогда сообщения других анонсов.
- **Инварианты Stage 28 сохраняются:** статусы
  `sending`/`partial`/`failed` не имеют `published_at`, `sent` имеет
  `published_at`; frozen `publication_text`/`publication_photos` и
  `publication_progress` согласованы, подтверждённые `ids` отделены от
  `previous_ids`. Продвижение уже доставленного live-блока в `sent`
  возможно только как проверенная транзакция с тем же текстом, фото,
  fingerprint и полным набором ID. Если текущие триггеры этого не позволяют,
  нужно добавить отдельный проверенный переход в новой миграции, **не**
  обходить триггеры и не помечать недоставленный пост как `sent`.

## 5. Длинный текст, фотографии, ошибки Telegram, рестарты

### 5.1. Лимиты (единая точка правды)

| Сценарий | Максимум текста | Что измеряем |
|---|---|---|
| без фото | 4096 символов | фактический текст после разбора Telegram entities |
| с одним или любым числом фото | 1024 символа | подпись к медиаблоку после разбора entities |

Запрещено разрезать длинный анонс на дополнительные текстовые сообщения,
автоматически его укорачивать или уводить подпись в отдельный текст. Пределы
применяются к целому анонсу. Исходники PTB могут использовать UTF-16 для
**смещений entities**; размер сообщения не следует автоматически приравнивать
к `len(utf16)` без проверки на Bot API. В тестах проверяются эмодзи, ссылки,
HTML entities, границы 1024/4096 и реальные ответы Telegram при ручном тесте.

### 5.2. Превышение лимита

Если готовый видимый текст не помещается в текущий лимит:

1. Надёжно сохранить и текст кирпичика, и новые `file_id` фото, с CAS.
2. **Не удалять** сообщение, которым пользователь ввёл вызывающий проблему
   текст/фото, даже если оно уже сохранено.
3. В нижнем экране показать фактическую длину, лимит, превышение и список
   самых длинных кирпичиков с прямой правкой, а также кнопку **«Изменить другой
   кирпичик»**, если предлагаемые варианты неудобны.
4. При наличии фотографий показать **«Без фотографий»**: это возвращает
   допустимый лимит к 4096, **не теряя текст**. Фото при этом остаются
   сохранёнными до подтверждённого отказа; пользователь может вернуть их
   позднее через редактор.
5. После правки пересчитать рендер и применить ожидавшую фотографию
   автоматически, если всё помещается. Остальные кирпичики повторно не
   спрашивать. Нет немого пропуска, деления текста или потери снимка.

### 5.3. Фотографии

| Свойство | Правило |
|---|---|
| Этап | после всех кирпичиков, одна явная инструкция «Отправьте фото или альбом» и кнопка «Без фотографий» |
| Завершение | завершённая Telegram-партия (одно фото или полученный альбом) → анонс готов **без** кнопки «Готово»; дополнительные партии через «Фотографии» готового анонса |
| Количество | **ровно 10 — окончательный максимум на один анонс** (решение владельца 2026-10-27). Попытка добавить 11-е фото отклоняется с понятным объяснением, ранее добавленные фото сохраняются. Хвост из одного фото в группе отправляется отдельным `sendPhoto`, потому что `sendMediaGroup` требует 2–10 |
| Альбомы | группа 2–10 в одном вызове `sendMediaGroup`; последовательность сохраняется |
| Вид | фото в верхнем блоке, текст после **последнего** фотосегмента; единственная подпись в **последнем** сегменте (как именно Telegram показывает подпись под альбомом — проверить на клиентах) |
| Изменение состава | нельзя просто добавить элемент к отправленной группе; сформировать новый согласованный медиаблок, подтвердить ID, потом очистить старый по возможности |
| Сохранение | Telegram `file_id`, последовательность ID доставленных фото/медиасообщений, fingerprint; каждый подтверждённый шаг записывается |
| Перенос при правке | уже выбранные фото **сохраняются**, заново выбирать их не требуется |
| Ограничение | Telegram может запретить удаление сообщения старше 48 ч; предупреждать о реально оставшейся версии |

Точный UX последовательности из нескольких **отдельных** фото в одном заходе
должен быть протестирован, чтобы не путать завершение Telegram-альбома с
отдельным сообщением и не вводить лишнее подтверждение. Приоритет —
согласованное автоматическое завершение после фото/альбома. Справка должна
объяснять, как послать несколько фотографий **одним альбомом**.

Если фото уже 10 и приходит ещё одно (или альбом), новые `file_id` **не**
принимаются в анонс, но и не теряются молча: нижний экран объясняет, что
лимит 10 исчерпан, предлагает удалить лишнее через «Фотографии» готового
анонса. Уже принятые фото не удаляются и не перезаписываются.

### 5.4. Матрица ошибок Telegram

| Ошибка | Обработка |
|---|---|
| `Bad Request: message is not modified` | игнорировать, не считать сбоем |
| `message to edit not found` | отправить сообщение заново, обновить id в БД |
| `MESSAGE_TOO_LONG` | проблемный экран §5.2, данные сохранены |
| `RetryAfter` (flood control) | подождать указанное время, один повтор; затем мягкая ошибка с сохранением данных |
| `Forbidden: bot was blocked` | остановить сценарий, ничего не удалять |
| `deleteMessage` старше 48 ч | логировать, продолжить (не сбой доставки) |
| частичная доставка медиагруппы | существующий `publication_progress`, честное предупреждение о возможном дубле |

### 5.5. Рестарты

| Момент рестарта | Поведение |
|---|---|
| до выбора площадки/личного шаблона | черновик ещё не создан; `/start` показывает меню |
| между вопросами | `stage=questions`, значения в БД, вопросы пересчитываются детерминированно |
| на шаге фото | состояние фото и уже принятые `file_id` в БД; незавершённая партия не дублируется |
| во время отправки | замороженный `publication_*`; только продолжение, без пересборки (уже реализовано) |
| после доставки | `completed`; восстановление по `draft_id` |
| Telegram-сессия потеряна | `EXPIRED_TEXT`; кнопки в «Мои анонсы» открывают анонс заново по `draft_id` |

Обязательное правило: восстановление никогда не создаёт новый снимок
шаблона и не переписывает значения.

### 5.6. Полностью пустой анонс и техническая заглушка

Решения владельца от 2026-10-27 (дополнение п.1–4).

**Что считается пустым.** Итоговый **видимый** текст пуст после рендера
секций по снимку: все кирпичики пропущены, и в шаблоне нет ни одного
литерального непробельного символа. Проверка выполняется по тексту без
HTML-тегов (`<b></b>` не делает анонс непустым) **после `strip()`**:
пробелы и переводы строк пустым текстом и считаются. Пример: шаблон с одним
литеральным `//` даёт видимый текст `//` — это **не** пусто, заглушка не
подставляется (решение п.2 важнее косметики).

**Правило заглушки:**

| Условие | Что отправляется как анонс |
|---|---|
| видимый текст непустой | рендер как есть (статика шаблона сохранена буквально) |
| видимый текст непустой + есть фото | рендер + фото |
| видимый текст пуст + есть фото | **только фото**, без текста-заглушки |
| видимый текст пуст + нет фото | ровно `.` (одна точка, без пояснений) |

- Заглушка — это **техническая необходимость**: Telegram не принимает
  сообщение с пустым текстом.
- В саму заглушку и в готовый анонс **не добавляются** содержательные
  тексты, подписи, шутки, «Ваш анонс пуст» и подобное.
- Заглушка не сохраняется как значение кирпичика и не попадает в
  `announcement_values`; она подставляется на этапе сборки сообщения.
- В `publication_text` фиксируется то, что реально уйдёт в Telegram
  (то есть `.`), чтобы замороженный payload совпадал с доставленным.

**Шутка в служебном сообщении.** Если анонс пуст, **нижний служебный
экран** показывает короткую шутку в штатном режиме с включённым юмором (дополнение п.4). Шутка живёт только
в служебном сообщении, никогда — в готовом анонсе. Источник шутки — модуль
редких вариаций (§5.7), но для пустого анонса показ **обязателен**, а не
вероятностный.

**Автотесты (обязательны):**

- пустой анонс без фото → отправлено ровно `.`;
- пустой анонс с фото → отправлено только фото, точки нет;
- шаблон из одного `//` → заглушка не подставляется, отправляется `//`;
- в отправленном тексте нет шутки и нет пояснений;
- нижний экран пустого анонса содержит шутку;
- непустой анонс не получает заглушку никогда;
- `.` не попадает в значения кирпичиков и не переживает правку.

### 5.7. Редкие юмористические вариации интерфейса

Решение владельца, дополнение п.5. Отдельный модуль, входит в **S5**.

| Свойство | Требование |
|---|---|
| Частота | ≈1% подходящих показов |
| Источник | заранее написанные шутки в коде/данных, **без вызовов LLM** |
| Что можно менять | текст вопроса или подпись кнопки |
| Что нельзя менять | `callback_data`, действия кнопок, состояние конструктора, порядок шагов |
| Запрещённые места | ошибки, права доступа, ограничения (лимиты), предупреждения о риске потери данных |
| Стабильность | при технической перерисовке того же экрана вариация сохраняется |
| Отключение | настройка, отключающая юмор полностью |
| Тесты | отдельно обычные и шуточные варианты |

**Механика «стабильной случайности».** Вариация выбирается детерминированно
из ключа экрана (`user_id` + `draft_id` + `stage`/`brick_id` + номер
показа), а не из `random()` на каждый рендер. Это гарантирует: повторная
отрисовка того же экрана (edit вместо send, обновление после рестарта)
показывает **ту же** формулировку, а следующий экран/следующий показ может
дать другую. Реализация — чистая функция
`pick_variant(key: str) -> str | None`, покрытая тестами на детерминизм.

**Границы модуля.** Отдельный файл (например
`Poster/utils/ui_humor.py`), без импорта Telegram-типов, без побочных
эффектов, без сети. Замена текста выполняется на уровне подготовки строки
экрана, **после** формирования `callback_data` и клавиатуры, чтобы
физически не иметь возможности их изменить.

**Отключение.** `UI_HUMOR_ENABLED` (имя на согласование при реализации);
при отключении функция возвращает `None` всегда, и ни один тест поведения
не зависит от шуток.

**Исключение для пустого анонса.** Дополнение п.4 требует шутку в нижнем
служебном сообщении пустого анонса **обязательно**. Это единственное место,
где шутка не вероятностная: при пустом анонсе `pick_variant` вызывается с
принудительным режимом (детерминированный выбор из набора, без 1%-фильтра).
Как этот обязательный показ сочетается с флагом отключения — см. §10 п.15.
Спецификация принимает вариант (а): **флаг отключения главнее**, при
выключенном юморе пустой анонс показывается без шутки.

**Что именно заменяется.** Только строка вопроса (например
«Как назовём анонс?») или подпись кнопки («Пропустить»). Список
разрешённых экранов задаётся белым списком константой модуля; всё, что не
в списке, юмор не получает никогда, даже при выпавшем 1%. Заголовки
секций, названия кирпичиков из данных пользователя и любые значения
подстановки не заменяются.

## 6. Стандартный шаблон, автоподстановка, сведения о площадке

### 6.1. Что должно быть обеспечено

1. Стандартный шаблон создаётся при создании площадки (есть).
2. **Каждый новый пользователь получает первый личный шаблон** из BUILTIN
   при создании профиля/первом `/start` (не после специального действия);
   уже зарегистрированным без личного шаблона — однократное дозаполнение.
   Идемпотентно. Если пользователь осознанно удалил все личные шаблоны,
   система **не восстанавливает** их самовольно при каждом открытии списка.
   Схема: `templates.kind='personal'`, имя «Мой шаблон», текст = BUILTIN.
3. **Статический текст шаблона сохраняется буквально.** Разделители,
   эмодзи, дефисы, `//`, `—` и любые другие литеральные символы остаются в
   результате даже при пустых кирпичиках. Удалять их как «мусор» или
   «сирот» **запрещено** (решение владельца, дополнение п.2). Схлопывание
   повторных пустых строк и удаление строк с висячими литералами — не
   вводится; это отменяет прежнее предложение спецификации.
4. Три секции сохраняются и остаются независимо редактируемыми (есть).
5. Автоподстановка — только для кирпичиков снимка (есть); id места брать
   **по коду**, а не хардкодом 5/6/7: `SYSTEM_BRICKS_BY_CODE["место"]`.
6. Стандартный шаблон содержит разделитель `//` между датой и временем
   начала (требование 4). `//` — часть статического текста, а не разделитель
   для склейки: он остаётся в готовом анонсе независимо от заполненности
   `[дата]` и `[время_начала]`.

### 6.1.1. Точный эталон стандартного шаблона (утверждён владельцем)

Шапка (жирным заголовок, строка даты/времени и название площадки):

```text
[название]

[дата] // [время_начала]
[место] (кликабельная ссылка при наличии URL)
```

Непосредственно под жирной шапкой отдельная **нежирная** строка `[адрес]`.
Тело — `[описание]`; подвал — `[контакт]`. Между шапкой, телом и подвалом
сохраняются предусмотренные шаблоном переводы строк. В итоговом Telegram
это один **реально отформатированный** анонс; строка `[место]` превращается
в гиперссылку на `ссылка_места` **только если URL существует и валиден**,
иначе остаётся обычным названием без пустых скобок или сырого URL.

Разделитель `//` — буквальная статика и не исчезает при пропусках.
Никаких дополнительных эмодзи, «🗓», «📍», лишней строки `🔗`, времени
окончания или пояснительного текста в стандартный шаблон не добавлять:
это **другие кирпичики**, которые автор может включить в изменённый шаблон.
Новый стандарт выдаётся и новым площадкам, и как первоначальный **личный**
шаблон. Реальный синтаксис жирности и условной ссылки следует реализовать
в поддерживаемой грамматике парсера/компилятора, а не хранить отображённые
здесь пояснения как буквальный текст шаблона.

### 6.2. Изменяемость значения внутри анонса

Значение из справочника попадает в `announcement_values` и правится только
в этом анонсе; `places.address`/`places.url` не меняются. Уже так работает:
`place_address`/`place_url` — снимок в черновике (`models.py:1146-1156`).
Требуется только UI: «✏️ Изменить» на автоподставленном кирпичике.

### 6.3. Кирпичик «Место» в личном шаблоне

`source='place'`, тот же самый справочник, что в режиме «Создать для
площадки», доступен по кнопке, **но внутри личного шаблона** допускается
свободный ввод имени разового места. Свободный ввод не создаёт запись в
`places`/`place_names`. Выбор зарегистрированной площадки заполняет кирпичик
«Место», а также присутствующие в **этом же личном шаблоне** кирпичики
`[адрес]` и `ссылка_места` из её карточки без повторных вопросов. Вход
по личному шаблону остаётся `origin=personal`, даже если его кирпичик
«Место» ссылается на существующую площадку. Альтернативное отображаемое
название выбранной площадки можно поменять в редакторе готового анонса.

### 6.4. Кирпичик адреса

Пользователь потребовал **системный кирпичик `[адрес]`** — официальный
почтовый адрес площадки (улица, дом и т. п.). В старой схеме существует
`адрес_места` с неизменяемым системным кодом. Целевой пользовательский
синтаксис — именно `[адрес]`, а не принудительное переименование требования
в `[адрес_места]`. Миграция должна добавить новый код/алиас, способный
ссылаться на тот же смысловой тип; прежний можно оставить лишь для чтения
старых снимков. Не нарушать CHECK/триггеры при обновлении системы.

### 7.5. Диагностика «владелец не видит админку»

Нельзя расширять права наугад. Проверяемые гипотезы (первый проход —
только чтение, затем точечное исправление подтверждённой проблемы):

1. `SUPERADMIN_USER_IDS` пуст или содержит не тот числовой ID
   (`config.py:28-32`): при нечисловом значении бот не стартует вообще.
2. Нет активной строки `place_admins` (`revoked_at IS NULL`) — передача
   админки не завершена.
3. Исключение в `_show_admin_button` проглочено → кнопки нет, а `/admin`
   работает (`handlers/main_menu.py:76-78`).
4. `track_user` не создал строку `users` → join не находит роль.
5. Смотрят на экран меню, отрисованный до выдачи прав (кнопка не
   перерисовывается сама).

Результат оформляется как отчёт «причина + доказательство», и только потом
предлагается правка (в конфиге, в данных или в коде — по факту). Никаких
«выдать права на всякий случай». Подтверждённую ошибку видимости или
привязки правильного числового ID **исправить**, не оставлять UX сломанным.

`[РЕШЕНИЕ ВЛАДЕЛЬЦА]` Открывать отдельный экран причин отказа для пользователей без прав
не требуется. Административные действия и глобальные настройки видны
только пользователям с проверенными полномочиями; при неудаче диагностировать
и исправлять ошибку **для владельца** по фактам, не раскрывая чужих данных.

## 8. Изменения БД и миграции

Правило проекта: миграции только добавочные; разрушительные — отдельный
план восстановления (`migrations.py:29-30`, `migrations.md`). Журнал,
checksum и авто-бэкап перед DDL уже есть.

### 8.1. Предлагаемая миграция 15 — описание и кирпичик адреса

Предлагается `ALTER TABLE bricks ADD COLUMN description TEXT` — поле
пояснения, которое автор кирпичика задаёт при создании/редактировании, а
создатель анонса видит в нижнем экране вопроса. Старые кирпичики имеют
`NULL`; тексты HTML-экранируются. Нужно также обеспечить **новый
пользовательский код `[адрес]`** с контекстной автоподстановкой официального
адреса площадки. Это может быть вставка системного кирпичика или
поддерживаемый парсером алиас к существующему `адрес_места`; выбор сделать
после проверки текущих индексов, уникальности кода, immutable-триггеров и
версий шаблонов. Не переименовывать существующий системный код напрямую.

### 8.2. Предлагаемая миграция 16 — черновик без площадки и живой медиаблок

Личный шаблон может не иметь кирпичика «Место»: `announcement_drafts.place_id`
должен допускать `NULL`. При этом `origin` — источник **шаблона** (`place` или
`personal`), а **не** место, выбранное впоследствии в кирпичике. Для
`origin='place'` требуется `place_id`, для `personal` его в черновике нет.
`place_name_id`, `place_display_name` и проверки их непустоты также должны
допускать отсутствие площадки, не делая разрешённым отсутствующее место
при `origin='place'`.

Предлагаемые изменения схемы (точные DDL/индексы и способ безопасной миграции
установить после ревизии текущего полного SQL):

```sql
place_id             INTEGER NULL;
place_name_id        INTEGER NULL;
place_display_name   TEXT NULL;
origin               TEXT NOT NULL DEFAULT 'place';
-- упорядоченные ID ВСЕХ сообщений живого блока (включая альбомы)
live_message_ids_json TEXT NULL;
-- состояние/ID нижнего экрана уже могут быть в existing UI state:
-- повторно не добавлять без анализа фактического хранилища
```

Один `live_message_id` **не годится** для мультимедийного блока из нескольких
сообщений. Сохранять должен каждый успешно подтверждённый ID; уникальность
версии и fingerprint нужны для недублирующей финализации и повторов.
Если найдено уже пригодное JSON-поле прогресса, **переиспользовать** его
вместо второй колонки. `live_message_ids_json` — контракт, а не приказ
создать поле с этим именем.

SQLite-перестройка таблицы затрагивает внешние ключи, индексы и триггеры:
сохранить определения и содержимое, выполнить бэкап до DDL, тесты миграции
с заполненными связанными таблицами, `foreign_key_check`, `integrity_check`,
равенство фактических строк/связей и идемпотентность повторного запуска.
Миграции 1–14 не менять. **Миграции 15/16 утверждены владельцем
2026-10-27** и исполняются с обязательными проверками целостности, rollback
и резервным копированием; на реальной базе во время разработки — нет,
только на временных SQLite.

Перестройка таблицы (§8.2) — это только схема. Контракт `place_id: int`

аккуратной передаче `None`, а не к переписыванию логики видимости.

### 8.5. Что происходит с автоподстановкой без площадки

Для `origin='personal'` и `place_id IS NULL`:

- `place_context_values` **не вызывается** (нечего подставлять);
- кирпичики `место`/`адрес_места`/`ссылка_места` (`source='place'`) не
  получают контекст и **становятся обычными вопросами**;
- если кирпичика «Место» в шаблоне нет — вопрос о месте не задаётся вовсе
  (требование 2: «Кирпичик „Место“ может вообще отсутствовать»);
- `places`, `place_names`, `place_admins` не затрагиваются.

Это единственная семантическая разница между двумя входами, и она
покрывается отдельным тестом (§ план, S1).

### 8.6. Совместимость: что будет со старыми черновиками

`announcement_drafts` может содержать собственные тестовые черновики.
Перестройка должна сохранять их значения, фото, снимки, revision и связи;
`origin='place'` для существующих записей с `place_id`, массив живых ID
первоначально пуст. Отсутствие живого ID не является поводом безусловно
досылать новую копию **уже завершённого** анонса: для него используются
подтверждённые `publication_progress.ids`, без дублирования.

7. **Документация.** `README.md` (106K), `stage18_architecture.md` §8–9 —
   пометить как исторические; актуальное поведение — в этом документе.

- `handlers/admin.py` — не переписывается; меняется только навигация.

### 9.3. Данные легаси

Poster ещё не выпущен. Конечная схема не должна бессрочно хранить лишние
таблицы и маршруты, но удаление допускается **только после** отключения всех
входов, переноса реально нужных функций, проверки зависимостей, резервного
копирования и **отдельного документированного решения** — когда доказано
отсутствие нужных данных и зависимостей (решение владельца 2026-10-27).
Не делать DROP в той же неттестированной операции, что и перестройку
`announcement_drafts`; верифицировать на временной копии.

Никакого требования конвертировать старые девятишаговые WIP в новый
конструктор нет. Завершённые анонсы нового конструктора остаются в чате.

## 10. Реестр решений: что утверждено, что предложено

**Утверждённые продуктовые правила (не спрашивать снова):**

1. **`[адрес]`** — отдельный понятный пользователю системный кирпичик
   официального адреса. Старый `адрес_места` — техническая деталь миграции,
   а не замена договорённого кода.
2. **Полностью пустой пост** разрешён; весь литеральный текст шаблона остаётся.
   Если видимого текста нет и фото нет — техническая `.`; если фото есть —
   фото без подписи. Шутка только в нижнем служебном сообщении.
3. **Ссылка площадки** — на названии `[место]` при наличии URL, без отдельной
   строки `🔗`; стандартный шаблон точно соответствует §6.1.1.
4. **Число фото** — **окончательный максимум 10 фотографий на один анонс**
   (решение владельца 2026-10-27, отменяет прежнюю формулировку «не
   утверждено»). Фото могут занимать несколько Telegram-сообщений: одна
   группа 2–10 в `sendMediaGroup`, хвост из одного фото — отдельным
   `sendPhoto`. Попытка добавить 11-е фото отклоняется с объяснением, уже
   принятые фото сохраняются. Архитектура хранения не ограничивается одним
   `message_id`.
5. **Длина** — 4096 без фото, 1024 с фото, после разбора entities.
   Unicode/HTML тестируются по фактическому поведению Bot API.
6. **Готовый пост редактируется отдельно**: данные/фото/extras можно менять,
   применение новой доставленной версии — по «Применить изменения».
   Изменение отдельного поля не рассылает копии.
7. **Фото при редактировании сохраняются** до явного изменения пользователем.
8. **Админка** живёт в «Управлении» и видна только при правах; права проверяются
   также в сервисах. Пропавшую у владельца кнопку надо **исправить по
   результатам диагностики**, а не ограничиться отчётом.
9. **Права владельцев личных шаблонов** не превращаются в доступ всех
   администраторов площадок к чужим личным данным.
10. **Новая площадка** создаётся из справочника «Создать для площадки»;
    сразу получает стандартный шаблон и запускает общий конструктор.
14. **BUILTIN обязан быть обновлён** под эталон §6.1.1, включая `//`,
    отсутствие лишних строк и стартовый личный шаблон. Это **не вопрос**.

**Инженерные предложения, утверждённые владельцем 2026-10-27:**

11. **Миграция 15** — `bricks.description` плюс механизм системного
    `[адрес]` (§8.1); предпочтительно простая аддитивная операция.
12. **Миграция 16** — `place_id NULL`, источник шаблона `origin`, хранение
    **всех** ID верхнего медиаблока (§8.2); нужна проверенная перестройка
    SQLite либо эквивалентный безопасный вариант. Фиктивная площадка не
    разрешается.
13. **Легаси-таблицы** — не удалять `drafts`/`user_states`, пока не доказан
    полный переход на новый конструктор и отсутствие нужных данных или
    зависимостей. Удаление — отдельная документированная операция с бэкапом,
    не в одной транзакции с перестройкой `announcement_drafts`.
15. **Юмор при выключенном модуле** — глобальный флаг отключает и шутку
    пустого поста; при включённом она всегда есть только в служебном экране.
    В остальных подходящих местах вероятность ≈1%.

Требования к миграциям 15/16 (обязательны, не обсуждаются): автоматические
проверки целостности (`foreign_key_check`, `integrity_check`, сверка строк и
связей до/после), rollback при сбое, резервное копирование перед DDL.

**Открытые детали для реализации (не блокируют утверждение продукта):**

- Реализация `[адрес]`: новая системная строка или алиас, проверив
  immutable-триггеры и поддержку существующих снимков.
- Хранилище `live_message_ids`: выделенная колонка или аккуратное
  переиспользование имеющегося JSON; важно не смешать с `publication_progress`.
- Точное распознавание конца Telegram-альбома/партии, чтобы автоматическая
  готовность не срабатывала до получения всех `file_id`.
- При сбое восстановления порядок нового верхнего блока и нижнего экрана,
  без ложных обещаний удалить сообщения старше 48 часов.

**Условие старта разработки:** **выполнено** — владелец утвердил эту
редакцию 2026-10-27 и поручил выполнить S1–S5. Менеджер самостоятельно
выбирает локальные технические детали в рамках документа и тестов, но не
вправе подменять перечисленные продуктовые правила новыми вопросами.

## 11. Риски

| Риск | Влияние | Смягчение |
|---|---|---|
| перестройка `announcement_drafts` | потеря/искажение связей и триггеров | бэкап, сохранение FK/индексов/триггеров, проверка содержимого и integrity на временной БД |
| `handlers/announcement_wizard.py` 5514 стр. | дорогие правки, конфликты | разбиение на 4 модуля в S3 до добавления живой панели |
| лимит 48 ч Telegram | дубли в чате | явное предупреждение, best-effort удаление |
| «живой» альбом нельзя редактировать по составу | мигание, неверный порядок, дубли | пересборка блока с ID каждого фото, создание нового нижнего экрана после блока, cleanup только после успеха |
| мусор легаси или потеря собственных тестовых WIP при удалении | удалить код и связанные таблицы в отдельном проверенном этапе после резервной копии; старую совместимость не поддерживать |
| monkey-patch в тестах | suite ломается при переносе | править тесты в том же этапе, что и код |
| большое число существующих тестов | долгие и хрупкие регрессии при удалении легаси | целевые тесты в этапах, общий `make check` и новые e2e с fake Telegram на финальном этапе |
| буквальное сохранение статики (§6.1 п.3) даёт «странные» анонсы (`//`, висячие эмодзи) | пользователь может счесть это багом | это осознанное решение владельца; в «Помощи» объяснить, что разделители — часть шаблона |
| шутка в служебном сообщении в неподходящий момент | выглядит неуместно | белый список мест, 1%, детерминированный ключ, полное отключение |
| шутка «протекла» в готовый анонс | порча продукта пользователя | отдельный слой отображения, тест «в анонсе нет шутки» |
| заглушка `.` не сохранилась в payload | расхождение замороженного и доставленного | `publication_text` = фактически отправленный текст, тест на совпадение |

## 12. Приёмка архитектуры и ограничения этой проверки

1. В меню **пять** кнопок: «📍 Создать для площадки», «📝 Создать по
   личному шаблону», «📂 Мои анонсы», «⚙️ Управление», «❓ Помощь».
2. Для площадки: сначала **все** доступные площадки, затем поиск и
   добавление; нажатие по названию сразу начинает общий конструктор без
   выбора шаблона и без подтверждения. Для личного — список своих шаблонов,
   CRUD и запуск по нажатию названия.
3. Первый личный шаблон и шаблон каждой новой площадки — точный BUILTIN
   из §6.1.1. Намеренное удаление всех личных шаблонов не создаёт новый
   при каждом входе в список.
4. **Один** конструктор и редактор, никаких `POST_STEPS`/`create_post` и
   «Новый мастер» как пользовательской функции.
5. Верх — отрендеренный анонс (до 10 фото несколькими группами,
   фото сверху, текст снизу), низ — одно редактируемое служебное сообщение;
   порядок сохраняется при замене верхнего блока.
6. Каждый кирпичик предлагается сверху вниз, может быть пропущен;
   зарегистрированная площадка и её адрес/ссылка автоподставляются только
   если соответствующий кирпичик есть в снимке; ручной ввод места никогда
   не заносит его в справочник.
7. Календарь виден сразу, без «Показать календарь»; время имеет
   18:00/18:30/19:00 и ручной ввод.
8. После вопросов — фото/«Без фотографий», потом **автоматическое**
   завершение без кнопки подтверждения и без второй отправки уже видимого
   поста. Повторный callback и рестарт не создают дублей.
9. Текст после entities не превышает 4096/1024; длинные кирпичики
   редактируются, фото и проблемный ввод сохраняются; есть «Изменить другой
   кирпичик» и «Без фотографий».
10. Завершённые анонсы остаются в чате при новом создании; при
    редактировании одного результата старая версия удаляется лишь после
    успеха новой доставки, если Telegram позволяет. Нижний экран не
    превращается в исторический мусор.
11. Разметка, ссылки, статический `//`, пустой пост (`.`) и шутка
    исключительно в служебном экране покрыты тестами.
12. «Управление» содержит площадки, шаблоны, кирпичики, админка показана
    только по правам; владелец с действительно выданными полномочиями
    получает рабочий вход, а не только диагностический отчёт.
13. Описания кирпичиков показываются во время ввода; пользователь понимает
    разницу между названием, кодом и описанием.
14. 1% вариаций интерфейса никогда не меняет callback, смысл действия,
    отправленный анонс и сообщения о рисках; при повторном рендере не
    «прыгает».
15. Регрессионные проверки: SQLite (FK/триггеры/ревизии), FakeBot e2e
    на 0/1/10 фото, частичную отправку, рестарт и отказ cleanup,
    `make check` для доступных Python; затем отдельный реальный Telegram
    ручной прогон владельца.

**Граница доказательств.** Эта редакция сделана по приложенным документам,
ранее согласованным в беседе решениям и официальной документации Telegram
Bot API. Локальный репозиторий, `AGENTS.md`, живая БД и работающий бот в
этой проверке **не открывались и не менялись**. Номера строк и исходные
диагностические наблюдения §1 сохранены из отчёта менеджера и должны быть
перепроверены в репозитории перед кодовой правкой.
