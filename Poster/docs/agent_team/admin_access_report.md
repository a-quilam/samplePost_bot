# Диагностика «владелец не видит админку» (Poster 2.0, S2, §7.5)

Дата: 2026-10-27. Проверка выполнена **только чтением кода и тестами на
временной SQLite** (`tests.test_stage20_admin_flow`). Реальная `.env` и
`post_bot.db` не открывались, бот не запускался — поэтому часть гипотез
проверяема лишь своим кодом, а не фактическими данными владельца.

Формат: **гипотеза → проверка → факт → вывод**.

## 1. `SUPERADMIN_USER_IDS` пуст или содержит не тот числовой ID

**Проверка.** `config.parse_superadmin_user_ids` (`config.py:22-56`):
пустая строка/`None` → `()`; элемент обязан быть ASCII-десятичным и > 0;
username отвергается; дубликаты схлопываются. `permissions.is_superadmin`
сверяет int и отсекает `bool`, `None`, ≤ 0.
`SUPERADMIN_USER_IDS` читается один раз при импорте `config`
(`config.py:83`) из `os.getenv` после `load_dotenv()`.
Тест: `tests.test_stage20_admin_flow.AdminMenuAccessTests`
(`patched_superadmin`) — при непустом списке кнопка администрирования
появляется, при пустом её нет.

**Факт.** Логика корректна и полностью покрыта тестами; нечисловое значение
не «молча игнорируется», а роняет старт (`ConfigError` → `ValueError`), то
есть тихая потеря прав по этой ветке невозможна. Значение в `.env` не
проверялось — это данные владельца.

**Вывод.** Статически **не подтверждена**. Проверка владельцем: в `.env`
должен стоять именно постоянный числовой Telegram user ID (не username),
и процесс должен быть перезапущен после правки `.env`.

## 2. Нет активной строки `place_admins` (`revoked_at IS NULL`)

**Проверка.** `permissions.has_any_place_admin_role` (`permissions.py:72-90`)
требует одновременно: строку `place_admins`, `revoked_at IS NULL` и join по
`User.telegram_user_id`. `can_access_admin_panel` = суперадмин **или** эта
проверка. Тесты `test_admin_button_visible_for_place_admin`,
`test_place_admin_opens_cabinet_with_own_place_only`,
`test_revoke_flow_clears_admin` проходят.

**Факт.** Роль администратора места выдаётся только завершённой передачей
(`handlers/admin.py`), «наследования» по созданию места нет — это
задокументировано в `place_store.create_place`. Если передача не доведена до
подтверждения, активной строки нет, и это ожидаемое поведение, а не баг.

**Вывод.** Статически **не подтверждена**. Проверка владельцем: наличие
строки в `place_admins` с `revoked_at IS NULL` для нужного `users.id`, либо
назначение себя суперадмином в `.env` (это штатный путь для владельца).

## 3. Исключение в `_show_admin_button` проглочено → кнопки нет, `/admin` работает

**Проверка.** Исходный код (`handlers/main_menu.py`, до S2):

```python
except Exception as e:
    logger.error("Не удалось проверить доступ в кабинет: %s", e)
    return False
```

`logger.error` без `exc_info`/`logger.exception` теряет traceback — при сбое
`can_access_admin_panel` (например, повреждённая сессия, занятая БД) в логах
остаётся одна строка текста, и отличить «нет прав» от «упало чтение» нельзя.
Сам отказ при этом **безопасен**: кнопка скрывается, `/admin` перепроверяет
права заново (`handlers/admin.py::open_admin`) и тоже отказывает — то есть
расхождение «кнопки нет, а `/admin` работает» этим кодом не объясняется.

**Факт.** Проглатывание исключения **есть**, но оно не создаёт описанного в
гипотезе расхождения: и кнопка, и `/admin` используют одну и ту же
`can_access_admin_panel` и при ошибке одинаково отказывают. Наблюдаемый
дефект — **диагностируемость**: причина скрытого отказа не попадала в лог.

**Вывод.** **Подтверждена частично (дефект наблюдаемости).** Исправлено:

```python
logger.exception("Не удалось проверить доступ в кабинет: %s", e)
```

Теперь при сбое в лог попадает traceback, и владелец может отличить
«нет прав» от «сломалось чтение прав». Права не расширялись.

## 4. `track_user` не создал строку `users` → join не находит роль

**Проверка.** `handlers/user_tracking.py::track_user` зарегистрирован в
`bot.py` группой `-1` (`TypeHandler(Update, track_user)`) и вызывается на
**каждый** Update до сценариев; внутри — `get_or_create_user` с UPSERT по
`telegram_user_id`, ошибка логируется и не блокирует обработку.
Тесты `test_start_registers_user`, `test_profile_updates_do_not_duplicate_users`
проходят: после `/start` строка есть, дублей нет.

**Факт.** Пропустить регистрацию можно только если Update вообще не дошёл до
приложения (неверная подписка `allowed_updates`, сеть) — а этот класс
инцидентов уже закрыт явным `allowed_updates=Update.ALL_TYPES` в `bot.py`.
Сама ветка «users есть, но join не находит» означала бы рассинхрон
`telegram_user_id`, чего код не создаёт.

**Вывод.** Статически **не подтверждена**. Проверка владельцем: строка
`users` с нужным `telegram_user_id` существует после любого действия в боте.

## 5. Смотрят на экран меню, отрисованный до выдачи прав

**Проверка.** `render_main_menu` (`handlers/main_menu.py`) вызывается на
`/start` и на callback `main_menu`; видимость считается **в момент
отрисовки** через `_show_admin_button`, без кэша в `user_data` или состоянии
экрана (`permissions.py` — «читают актуальное состояние БД при каждом
вызове»). Тест `test_admin_panel_callback_denied_does_not_change_screen`
фиксирует, что старый экран не перерисовывается сам.

**Факт.** Поведение ожидаемое: Telegram не перерисовывает чужие сообщения, и
старый экран показывает старое меню. После `/start` (или «🏠 Главное меню»)
меню строится заново по актуальным правам.

**Вывод.** Статически **не подтверждена как дефект кода** — это
ограничение интерфейса Telegram. В S2 смягчено: администрирование переехало
в подменю «⚙️ Управление», которое всегда открывается заново и считает
видимость при каждом входе.

## Итог

| # | Гипотеза | Статус | Действие |
|---|---|---|---|
| 1 | `SUPERADMIN_USER_IDS` пуст/неверен | не подтверждена статически | нужны данные владельца (`.env`) |
| 2 | Нет активной `place_admins` | не подтверждена статически | нужны данные БД |
| 3 | Исключение проглочено в `_show_admin_button` | **подтверждена частично** | исправлено: `logger.exception` |
| 4 | `track_user` не создал `users` | не подтверждена статически | нужны данные БД |
| 5 | Экран отрисован до выдачи прав | не подтверждена (ограничение Telegram) | вход через «⚙️ Управление» |

Ни одна гипотеза не даёт статически доказанной **потери прав**: единственная
подтверждённая проблема — немая диагностика скрытого отказа, она исправлена
без расширения прав. Полная проверка гипотез 1, 2, 4 требует фактических
значений `.env` и строк `users`/`place_admins` на реальной базе — эти данные
владелец предоставляет отдельно, и по ним при необходимости принимается
решение (конфиг/данные), а не «права на всякий случай».
