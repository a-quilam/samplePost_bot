# План исправлений Poster 2.1 (R1–R5)

Дата: 2026-10-28. Основание: первый ручной тест владельцем бота
@samplePost_bot — дефекты №20–30. База: HEAD `11ab54e` (S1–S5 приняты).

## Контекст

Poster 2.0 (S1–S5) реализован и принят. Владелец провёл первый ручной тест и
нашёл дефекты UX и логики. План делит исправления на 5 этапов с процедурой
«разработчик → независимые тесты → ревизия → приёмка → commit+push».

## Реестр дефектов владельца

- №20 — не зафиксирован отдельно в задании; трактуются как суммарное
  недовольство стабильностью после №21–29 (уточнение в R4-отчёте).
- №21 — назначение админа места: ввод `@a_quilam` «ничего не дал»; нет
  явного результата (назначен / уже есть / не найден / нет прав / неверный
  формат).
- №22 — «Альтернативные названия»: «◀️ Назад» даёт «Произошла внутренняя
  ошибка», затем «Кнопка устарела». Корень: `adm_cancel` в фазе
  `edit_aliases` не входит в allow-list `handle_cancel_flow`.
- №23 — легаси reply-клавиатура «Создать пост»/«Черновики» осталась у
  клиентов; при входе не отправляется `ReplyKeyboardRemove`.
- №24 — навигация «Глобальные предложения» / «Предложения по местам»
  непонятна; упростить без удаления функциональности.
- №25 — «Управление → Шаблоны» запускает создание анонса; разделить
  создание и управление шаблонами.
- №26 — «Управление → Площадки» — не настоящий справочник/карточка с
  действиями по правам.
- №27 — описание кирпичика: предпросмотр «Сейчас:» не моноширинный
  (`<code>`).
- №28 — «Мои кирпичики» захламлён; строки = название + компактная кнопка
  предложения; короткие подписи; упрощение хаба.
- №29 — карточка предложения кирпичика без описания (снимок не хранит
  description).
- №30 (глобальные кирпичики) — глобальное одобрение отклоняется из-за
  локального кирпичика места с тем же кодом: `check_code_availability(
  scope="system")` отклоняет при `any_row` с тем же кодом. Глобальный
  должен побеждать для новых привязок; локальный конфликт — отдельная
  задача на разрешение.

## Этапы

### R1 — Стабильность и критичный UX
Файлы: `handlers/admin.py`, `handlers/main_menu.py`, `handlers/user_tracking.py`,
`utils/screen.py` (+ точечные правки входов). Запрещено: менять схему БД.
1. №22: `edit_aliases` в allow-list `handle_cancel_flow`; аудит всех
   переходов «Назад» по фазам admin.py (каждая кнопка `adm_cancel` должна
   вести к допустимой фазе-цели).
2. №23: `ReplyKeyboardRemove` на `/start` и входах в UI (главное меню,
   конструктор, админка); регресс-тест, что после входа reply-клавиатуры
   больше нет.
3. №21: при поиске получателя (`assign_search`): поддержка ввода `@username`,
   явные результаты — назначен / уже админ / не найден / нет прав / неверный
   формат; никакого «молчания».
4. №30 (только стабилизация, без миграции): `check_code_availability` для
   `scope="system"` не должен считать занятым код, существующий только в
   других областях (place/personal); уникальность сохраняется внутри
   области system. Полная модель конфликтов — R3.

Критерии: все 4 пункта; полный `make check` зелёный; новые тесты на каждый
пункт; ревизия без блокирующих замечаний.

### R2 — Шаблоны и разделы «Управление»
Файлы: `template_types.py`, `template_store.py`, `template_compiler.py`,
`handlers/templates.py`, `handlers/main_menu.py`, `handlers/places.py`,
`handlers/bricks.py` (частично), `handlers/admin.py` (частично).
1. BUILTIN v3: точный формат Части III (жирный заголовок, пустая строка,
   жирная «дата // время», жирная кликабельная площадка, адрес отдельной
   строкой, пустая строка, описание, пустая строка, контакт; `//`
   сохраняется буквально при пропусках; пустой результат → `.`).
2. Миграция 18 (или ближайший номер): обновление только нетронутых копий
   BUILTIN-шаблона по маркеру `TemplateVersion.builtin_version`; права
   человека не трогаются. Переименование стартового личного шаблона в
   «Дефолтный шаблон».
3. Явное действие «Восстановить стандарт» в карточке шаблона.
4. №25: «Управление → Шаблоны» — только просмотр/создание/правка/удаление/
   восстановление; создание анонса запускается только из главного меню
   и из раздела создания. Удаление шаблона не ломает FK (снимки/архив).
5. №26: «Управление → Площадки» — справочник с карточкой места и действиями
   по правам; создание площадки выдаёт стандартный шаблон; тап по площадке
   в режиме выбора сразу запускает конструктор.

Критерии: рендер BUILTIN v3 побайтово по Части III; миграция на копии
реальной БД — только на тестовых копиях до деплоя; новые тесты рендера,
миграции, прав доступа; ревизия approve.

### R3 — Глобальные кирпичики и конфликты кодов
Файлы: `brick_store.py`, `brick_proposal_store.py`, `models.py`,
`migrations.py` (миграция 19+), `handlers/bricks.py`, `handlers/admin.py`.
1. Модель конфликта: одобрение глобального кирпичика при существующем
   локальном (place/personal) с тем же кодом — разрешено; глобальный
   выигрывает для новых привязок немедленно.
2. Автосоздание задач разрешения конфликта по местам; идемпотентные
   уведомления админам; история решений сохраняется (снимки неизменяемы).
3. Обязательное разрешение: переименовать локальный ИЛИ переключиться на
   глобальный (с обновлением привязок шаблонов).
4. Минимальная схема: новая миграция (таблицы задач/состояний), никаких
   перестроек существующих таблиц без необходимости.

Критерии: негативные тесты (конфликт, гонка двух решений, рестарт между
шагами); идемпотентность уведомлений; ревизия approve.

### R4 — UX-чистка и чат как приложение
Файлы: `handlers/announcement_wizard.py`, `handlers/wizard_live.py`,
`handlers/bricks.py`, `handlers/admin.py`, `utils/screen.py`.
1. Чат как приложение: после успешной обработки удаляются устаревшие
   экраны и ввод; один живой блок анонса сверху, один служебный экран
   снизу; альбомы не дробят порядок; отказ Telegram на удаление —
   безопасно (данные не теряются).
2. №24: навигация предложений — понятные разделы, хлебные крошки,
   короткие подписи, без потери функциональности.
3. №27: предпросмотр описания в `<code>`.
4. №28: хаб кирпичиков — строки «название + компактная кнопка предложить»,
   добавить/навигация/пагинация, короткие подписи.
5. №29: карточка предложения — название, код, тип, описание, автор, цель,
   статус (хранение description в снимке при необходимости — согласовать
   с миграцией R3 или отдельной миграцией).
6. Юмор: остаётся ~1%, детерминированным, никогда не в публикуемом тексте
   и предупреждениях, отключаемым.

Критерии: сценарии чат-как-приложение (мультиэкран, альбом, рестарт,
отказ удаления); ревизия approve.

### R5 — CI, тест-матрица, очистка данных, деплой, отчёт
1. Автоматизация частей A–G тест-матрицы владельца (по мере покрытия
   R1–R4; добить оставшиеся случаи).
2. После зелёного CI: остановить `poster-bot.service` (systemctl --user),
   WAL-aware бэкап реальной БД с `PRAGMA integrity_check` +
   `foreign_key_check`, зафиксировать путь/размер/SHA-256/версию схемы.
3. Чистая БД: предпочтительно новая БД через штатный механизм (миграции с
   нуля); сохранить код, миграции, системные кирпичики, стандартный
   шаблон, конфиг/токен/systemd/proxy, ID владельца и суперадмин-права.
4. Деплой: `poster-bot.service` + `tg-connect-proxy.service` активны и
   enabled; Telegram-авторизация, polling, логи, нет рестарт-петли,
   интервал стабильности. Не трогать сеть/SSH/проектор.
5. Финальный отчёт владельцу (разделы 1–8).

Критерии: бэкап верифицирован ДО любых действий с реальной БД; бот
стабильно работает на чистой БД; отчёт составлен.

## Процедура и ограничения

- Делегирование: `poster-developer` (реализация) → `poster-tester`
  (независимые сценарии) → `poster-reviewer` (ревизия) → приёмка.
- Менеджер код не пишет; макс. 2 параллельных подагента, один писатель.
- `opencode.jsonc` вне коммитов этапа. Реальная БД не мигрируется до R5.
- Работающий бот не останавливать до этапа R5 (кроме R5 по плану).
